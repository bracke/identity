identity release gates
======================

How to run
----------

    ./tools/release-check.sh

CI runs exactly this script on every push and pull request
(.github/workflows/release-check.yml) and uploads generated/evidence/ and
generated/release/ as artifacts. If the workflow and the script ever disagree,
the script is the definition.

That script is the release gate. It builds the library, runs every suite,
records each run's real outcome under generated/evidence/, and only then runs
identity_tools, which validates the registries and generates the release
reports in generated/release/ from that evidence. It exits non-zero if any
gate fails. Nothing downstream should treat generated/release/ as meaningful
unless release-check.sh exited 0 in the same run that produced it.

The repository SPI
------------------

Public operations depend on Identity.Adapters.Repositories.Stores.Store_Interface,
not on any adapter. Three adapters implement it:

- Memory     -- the reference in-memory store (not task-safe).
- Persistent -- write-through to a snapshot file after every mutating call;
                the only adapter that touches real I/O.
- Recording  -- wraps any store and counts delegated calls; exists to prove the
                SPI is pluggable rather than merely declared.
- Serialized -- wraps any store behind one lock to make it safe to share
                between tasks; reports Concurrent_Access in its capabilities.

The conformance harness runs all five certification profiles against the
memory, recording and persistent adapters through the identical code path, and
afterwards reloads the persistent adapter's snapshot into a fresh store to
check that durability actually held rather than assuming it.

Durability is per call, not per transaction: a multi-command sequence is not
atomic as a whole.

Enforced gates
--------------

Each of these fails the release check when it fails. "Evidence" means the gate
records its outcome to generated/evidence/<name>.txt; identity_tools refuses to
generate release reports if any evidence file is missing or records a failure,
so a suite that never ran cannot be reported as satisfied.

- alr build of the library under -gnatwe (warnings are errors)
- crates/identity_tests AUnit assertion suite                    [evidence: aunit]
  Includes dedicated blocks, each assertion message carrying its prefix:
  atomicity: (failed commands leave no partial mutation), disclosure:
  (untrusted projections collapse distinct causes), events: (registry and
  schema consistency) and emission: (each event type produced by the audited
  operation that emits it).
- crates/identity_conformance repository conformance             [evidence: conformance]
  Runs 39 real commands and queries against the in-memory store across the five
  certification profiles, and fails a profile unless the number of checks
  actually executed equals Required_Check_Count for that profile.
- crates/identity_examples identity_lifecycle walkthrough        [evidence: examples]
- concurrency suite (identity_concurrency)                       [evidence: concurrency]
  16 tasks contend for the same identifiers through the Serialized adapter and
  the tally must come out exact: one Applied per identifier, every other attempt
  a uniqueness conflict, every stored principal still readable. Detection of a
  broken lock is probabilistic by nature -- measured at 9/10 runs against a
  deliberately disabled lock, with no false failures in 10 runs against a
  correct one.
- GNATprove over registries/proof-scope.json                     [evidence: gnatprove]
  Fails on any unproved check, any SPARK legality error, and any non-excluded
  proof-scope package that was not analysed. Currently 616 checks, 0 unproved.
- tools/gate-selftests.sh gate self-tests                        [evidence: gate-selftests]
  Mutation-tests the gates themselves: each case copies the tree, breaks one
  piece of evidence, and requires identity_tools to fail with that gate's own
  marker. Proves the gates fail closed rather than passing vacuously.
- identity_tools registry and source validation:
  - project_tools workflow manifest (required workflows, gates, orchestration)
  - release artifact and prohibited-material inventory
  - crypto algorithm registry (binding, format versions, constant-time,
    separated creation/verification permissions, deprecation state)
  - persisted-format registry and deterministic fixture inventory
  - invariant traceability: every name under "required_tests" in
    registries/invariants.json must appear verbatim in a real evidence source
    (the AUnit suite, the gate self-tests, the conformance harness, or the
    examples). Metadata presence alone is not accepted.
  - event registry coverage against the public event constants
  - architecture boundaries: no Identity.Internal dependencies from public
    code, cryptolib imports confined to the Identity.Crypto.CryptoLib.*
    subtree, no authorization-boundary vocabulary
  - canary secret-leak scanning over docs, registries, fixtures, tools,
    examples and conformance output
  - capability backing (marker identity_tools:capabilities). Every flag that
    Full_Memory_Profile advertises as True must have its backing SPI primitive
    actually called from the operations layer, because Admit_Transaction and
    Admit_Command make admission decisions from those flags. An advertised
    capability that nothing implements is reported as
    capabilities:advertised-but-unbacked:<flag>:<primitive>. Mandatory events
    additionally require the reserve-before-mutate call, reported as
    capabilities:unreserved:<flag>. The audit helper itself is excluded from
    the scan: counting it would prove only that the helper exists, not that
    any operation calls it.
  - documentation checks (marker identity_tools:documentation). Five checks,
    each of which fails the release check on its own:
    1. every documentation artifact named with a .md path in
       registries/release-artifacts.json exists and is non-empty
       (documentation:missing-artifact-document:<path>)
    2. the required documentation set exists and is non-empty: README.md,
       CHANGELOG.md, SECURITY.md, CONTRIBUTING.md, CODE_OF_CONDUCT.md, LICENSE,
       docs/architecture.md, docs/threat-model.md, plus every docs/ai/*.md
       that another document links to
       (documentation:missing-required:<path>, documentation:empty-required:
       <path>, documentation:missing-referenced:<path>)
    3. no documentation file carries an unresolved placeholder marker
       (documentation:placeholder:<path>:<marker>)
    4. every top-level Identity.<Area> family present under src/public is named
       in docs/ai/package-map.md (documentation:unmapped-area:<area>)
    5. CHANGELOG.md carries a section heading for the crate version declared in
       alire.toml (documentation:missing-changelog-section:<version>)

Audit events
------------

Security-relevant transitions emit an event through Identity.Operations.Audit.
Because a transition and its audit record must be inseparable, an operation
reserves event capacity BEFORE mutating (Audit.Capacity_Reserved) and appends
after the transition (Audit.Emit); a store that cannot accept the event refuses
the operation rather than applying a change nobody can audit. Conflicts are
audited as well as successes, so a rejected attempt still leaves a record.

Emission is added as an overload on each operation, so callers that do not pass
an operation context keep working unchanged -- and produce no audit trail. Code
that needs an audit trail must use the context-taking entry points.

Replay protection
-----------------

Five operations are triggered from outside and cannot be safely repeated:
password reset request, contact verification request, recovery begin, API key
issue and session rotate. These are exactly the members of
Identity.Operations.Idempotency.Idempotent_Operation_Kind, and each now offers
an overload taking an idempotency key alongside the operation context. That
overload reserves the key through the SPI (Stores.Reserve_Idempotency) BEFORE
the transition and closes the record (Stores.Complete_Idempotency) after it
applies, so Full_Memory_Profile advertises Idempotency => True and the
capability gate finds a real caller behind the flag.

The semantics, kept identical across the five:

- Fresh reservation: the transition runs. If it applied, the record is closed
  and the verdict is Fresh. If it did not apply, the record stays open --
  nothing happened, so nothing may later be replayed under that key.
- Replayed reservation: the recorded outcome is returned and the transition is
  NOT performed again. This is the whole point: no second reset token, no
  second API key, no second recovery transaction, and no second audit event.
- In_Progress, Conflict, Capacity_Exceeded, Infrastructure_Failure: the
  transition is refused and the store is left untouched. In_Progress means an
  earlier attempt under this key never completed; a caller that wants the
  transition attempted again must present a fresh key.
- An empty key is refused without touching the store, because every empty key
  compares equal to every other and would collide across unrelated requests.

The verdict carries both halves -- what the store did and whether this call is
what did it -- in Identity.Operations.Replay.Command_Outcome (or
Recovery_Outcome for the recovery transition status). Command_Status has no
infrastructure verdict of its own, so a store fault reported by the reservation
collapses onto State_Conflict while the decision half keeps the cause.

Existing signatures are untouched: a caller that passes no key keeps the old
behaviour and gets no replay protection, exactly as with audit emission.
Identity.Operations.Replay declares only the shared result shape and the
mappings; every reservation is made by the operation itself, so the capability
is backed by the operations rather than by a helper standing in for them.

Recovery begin gained an audited overload in the same change, emitting
identity.recovery.began, since its idempotent form mutates through the SPI and
must therefore leave a record like every other mutating operation.

Be precise about what the audit-coverage gate proves. It requires every
mutating operation to OFFER an audited path; it cannot require callers to take
one. The marker reports both numbers -- audited-overloads and bypass-overloads
-- and the bypass figure is large (currently 111 plain overloads against 48
audited ones), because emission was added additively so existing callers kept
compiling. Any of those plain overloads still mutates without leaving a record.
Closing that surface means removing the plain overloads, which is a breaking
change deferred past V1.

The event vocabulary is 51 constants, and the events gate requires the registry
and the public constants to agree exactly (identity_tools:events, currently
51/51). The suite drives the audited emission cases through their operation,
each asserting that the audited overload appends exactly one event while the
plain overload of the same operation appends none, and -- since the SPI gained
Find_Event -- reading the recorded envelope back to assert its actual Type_Id
and Outcome rather than inferring them from which branch was reachable.

Not every one of the 51 types has an emission case: the suite covers the
sixteen that existed when those tests were written. The audit-coverage gate is
what guarantees the remaining types are emitted by some operation; the suite is
what checks the recorded contents of the ones it covers.

Cost
----

A full release check takes about five minutes, dominated by the AUnit suite
(~2 minutes). That is PBKDF2 at 600,000 iterations: every operation that
creates or verifies a password verifier costs roughly 0.6 s, and the suite now
performs a few hundred of them. It is real work, not waste -- lowering the
iteration count to speed the suite up would weaken the thing being tested --
but the trend is worth watching as more audited operations gain tests.

Known gaps
----------

- Proof covers 11 packages, not the library. GNATprove discharging 760 checks
  with none unproved is a real result, but it is a result about
  registries/proof-scope.json: ten proved packages and one justified
  exclusion, against 369 public and adapter specs. Identity.Crypto.
  Password_Hashing is now included, and specifically its envelope parser --
  the code that consumes attacker-controlled text -- with Create_Verifier,
  Verify and Derive_Verifier left outside SPARK because they reach cryptolib
  and borrow controlled secret bytes. Still outside the scope entirely:
  Identity.Crypto.Secret_Verifiers, .Constant_Time, Identity.Secrets.Bytes and
  .Secrets.Text. Their bounds rest on review and tests, not proof.

These are listed as mandatory above the line in earlier revisions of this file
but are NOT yet enforced. They are recorded here rather than being described as
implemented.

- Password verifier migration is caller-driven. Identity.Operations.Passwords.
  Migrate_Verifier re-derives a below-policy verifier during a successful
  authentication, but nothing forces a caller to invoke it: a replacement
  credential needs an identifier and this crate never invents identifiers.
- A Memory.Store is 3.3 MB (fixed-capacity arrays sized for 512 events, 128
  sessions and so on), so two of them will not fit on a default 8 MB stack.
  Harnesses that need isolated stores must allocate them on the heap, as the
  conformance and concurrency harnesses do; the AUnit suite instead shares one
  store and uses distinct identifier prefixes, which is weaker isolation.
